### 策略模式

定义：策略模式定义了算法族，分别封装起来，让它们之间可以互相替换，此模式让算法的变化独立于使用算法的客户

适用场景：
    适用于适合使用继承的复用功能，但又担心出现因继承导致子类被父类污染的情况。
    策略模式适用于替换继承模式，将原本由基类定义的让子类继承使用的方法 抽象成行为类。然后将这些行为类挂在原本的基类上。
然后子类根据自己的实际情况，复用具体实现的行为类的子类或新实现行为类。这样，可以在保证不重复实现的情况下，依然有复用的效果。

理解性阐述和介绍：
    想象以下场景：
        基类的某个方法，它的所有子类实现方式都是一样的，那么直接在基类上实现这个方法，所有的子类都可以直接复用这个方法，这也是继承的优势所在。
        但是如果新增的子类，对这个方法的实现是不同。那么，在实现这个新增的子类时，需要覆盖基类的方法，并给出具体实现。
    继承的弊端就在这里，，，在没有这个子类之前，直接在基类上实现公共的方法是很合适的。但是，当需要变动需求或者有新需求出现时，就没有那么方便了
    比如，新增一个橡皮鸭子，它是不会飞的，那么就需要在橡皮鸭的子类中覆盖掉fly方法（说实话，，，如果只是新增这一个，需要覆盖一个方法，覆盖就覆盖了，这个感觉还好吧）
    再比如，新增一个诱饵鸭，它既不会飞也不会叫，那么就需要在诱饵鸭的实现中，覆盖掉fly方法和quack方法（随着需求越来越复杂，之前设计的继承结构越来限制新需求的实现）
        随着新需求的出现，会出现越来越多的鸭子。这些鸭子彼此之间既有共性，又有不同之处。
        如果我们抽出鸭子们行为a的最大共性写在基类上，虽然可以最大程度上利用继承复用代码，但是与基类行为不同的子类均要覆盖父类的方法，
    并自我实现，，，这样似乎也没有什么问题，但是实际上，这些不满足最大公约数的子类方法，或许也存在三三两两的相同实现。如果我们只是使用继承来重复代码，那只能减少一种重复的代码。
        但是如果我们采用策略模式，即把某种方法抽象成一个方法类，那么我们就可以把所有子类的此方法，将相同的实现实例化成一个方法类，保证最大限度的的复用代码。并且如果后续的新增类
    的方法有不同，直接新写一个继承方法基类的方法类就好了。

### 遵循的设计原则：

找出应用中可能需要变化之处，把它们独立出来，不要和那些不需要变化的代码混在一起。
针对接口编程，而不是针对实现编程
多用组合，少用继承
